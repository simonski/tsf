# CLI Harness Tutorial

## Purpose

The CLI harness is a fast Go integration test that runs real terminal commands against a temporary in-memory-style test environment (temp DB + HTTP server).

It validates CLI behavior from a markdown scenario file and writes an adapted markdown report with expected vs actual results.

## Files

- Scenario spec: `docs/CLI_HARNESS.md`
- Harness runner code: `internal/cliharness/harness.go`
- Integration test entrypoint: `cli_harness_integration_test.go`
- Generated report: `docs/generated/CLI_HARNESS_REPORT.md`

## Run It

Run just the CLI harness test:

```bash
go test -run TestCLIHarnessFromMarkdown ./...
```

Run all Go tests (includes harness):

```bash
go test ./...
```

Run focused server tests for project file/note/comment features:

```bash
go test ./internal/server -run 'TestProjectFileAndNote|TestEntityComment' -v
```

Run Playwright E2E coverage for these features:

```bash
cd tests/e2e
npx playwright test specs/project-assets-comments.spec.ts
```

## Scenario Format

Scenarios are markdown/plaintext blocks delimited by 80 dashes:

```text
--------------------------------------------------------------------------------
name: project list
cmd: sf project ls
exit: 0
stdout: Found
--------------------------------------------------------------------------------
```

Supported keys:

- `name`: Friendly test name
- `cmd`: Full terminal command (start with `sf ...`)
- `exit`: Expected exit code (default `0`)
- `stdout`: Substring(s) expected in stdout (`;;` separated)
- `stderr`: Substring(s) expected in stderr (`;;` separated)
- `capture`: Regex capture for variables (`;;` separated)

Capture format:

```text
capture: task_id="id"\s*:\s*"([^"]+)"
```

Use captured variables in later commands:

```text
cmd: sf task get -task_id ${task_id}
```

## Report Output

After test execution, report is written to:

- `docs/generated/CLI_HARNESS_REPORT.md`

The report is an adapted copy of each scenario block with appended:

- `actual_cmd`
- `actual_exit`
- `pass`
- `failure` (if any)
- output snippets (`actual_stdout`, `actual_stderr`)

## Tips For Fast, Stable Tests

- Prefer deterministic IDs where possible (`-project_id`, `-role_id`, etc.)
- Use captures only when IDs are generated by the API
- Keep expectations to stable substrings, not full output
- Keep scenarios ordered and state-aware
